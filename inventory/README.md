# Simulated store inventory

Every inventory surface displays:
**Demo inventory — simulated, not live availability.**

No seed assignment is evidence that a store carries a brand/product, has an
allergy-safe product, or has stock today. No quantities, prices, real-time feeds,
ingredient labels or allergen claims are generated by this system.

## Deterministic data and persistence

`data/demo-v1.json` freezes the 17 existing store IDs and 50 existing product IDs.
`seed.ts` uses a versioned, stable FNV-1a hash of the seed/store/product IDs to
assign products and statuses. It uses no randomness, date, device ID, geography,
chain-specific assortment assumption, API or network request. Sorted input IDs
produce identical output regardless of manifest order. Existing v1 assignments
must not be changed by editing the algorithm; a future seed version needs an
explicit review/update policy.

The v1 seed creates **671 pairs**: **389 in stock**, **146 limited stock** and
**136 out of stock**. Each store has 35–43 assigned products; all 50 products are
represented somewhere. An unassigned pair is unknown, not out of stock. Out-of-
stock demonstration products remain browsable with an explicit label.

Migration 6 adds `store_inventory.simulated_status` without replacing its original
table, primary key, foreign keys, `is_demo = 1` constraint or legacy status field.
Existing available/unavailable rows map to in_stock/out_of_stock; unknown remains
unknown. Migration 7 enforces consistency between known simulated and legacy
status values on subsequent writes. Unknown is retained for unclassified/manual
demo entries. Migrations 1–5 are unchanged.

`demo_inventory_entries` records ownership with a composite foreign key to the
original inventory row. `importDemoInventory` validates the seed, uses bound SQL
and one transaction, serializes imports on a connection, and relies on product/
store foreign keys. A failure rolls the batch back. Repeated imports write no new
rows or status changes. Existing unowned pairs and pairs owned by another seed
are skipped. Even owned rows are not overwritten on repeat import. Removing an
ID from the manifest never deletes inventory. Normal database initialization
awaits product/store imports before this seed, all in the existing `foodbuddy.db`.

Only inventory and ownership tables are written. Product evidence, sources,
verification dates, user accounts, sessions, profile pictures and saved allergy
profiles are not updated. No allergy-checker or derivative implementation,
mapping, data or existing test file was changed for this step.

## Browsing and details

`localProductService` accepts an optional `storeId` in search/browse options and
category counts. It joins only that store's demo inventory, retains deterministic
pagination, and returns a separate `simulatedAvailability` summary field. Name/
brand matching, escaping and category filtering use bound SQL. Without `storeId`,
search/browse still covers all 50 products and returns no implied stock status.

Nearby Stores' selected-store panel offers **View demo inventory**. The product
screen supports an optional store context: store name/address, disclaimer,
stock labels, search, category chips/counts, empty results and pagination. Search
and category filters combine within the store. The same existing detail-loading
effect and `checkLocalProductAllergies` call are reused unchanged. Inventory does
not change ingredient verification, incomplete-information warnings or packaging
reminders. Selecting an out-of-stock demo item still opens its product details.

The map screen remains mounted beneath an opaque inventory overlay, with map
interaction/accessibility disabled while browsing inventory, so Back retains
its selected store, camera and current location state. Existing tab navigation is
preserved. Apple Maps may use internet normally; offline map tiles are not a
requirement. No local backend, Wi-Fi host address or grocery credentials are used.

Global product details offer a collapsed **View demo store availability** action.
`localInventoryService` reads only assigned store/product pairs and returns their
explicit demo status. No assignments produce an unknown-availability empty state.
This optional panel never requires selecting a store to use global search.

## Validation

Run `node --experimental-sqlite --test tests/*.test.cjs` and
`npx --no-install tsc --noEmit`. New tests in `tests/inventory.test.cjs` cover
deterministic generation, imports/repeats/concurrency, ownership protection,
rollback/foreign keys, status constraints, v5 upgrades, scoped search/category
filtering/pagination, missing evidence and preservation of user/product/store
data. All pre-existing test files remain unchanged. The existing allergy checker
is used as-is; derivative work remains owned by the teammate.

iOS simulator testing invokes rendered UI handlers through the localhost Metro
debugger, reads native SQLite results through the UI, and uses screenshots. It
does not substitute for physical-device touch/hit testing. Tested pin → correct
store inventory, 24-row initial pagination, 41 total Target Charleston South
products, Breakfast filtering and case-insensitive search, incomplete LaCroix
details, return to retained map selection, global 50-product browsing, and optional
global Oreo demo availability. No JavaScript fetch calls occurred during that flow;
native Apple Maps networking remains allowed. Temporary test helpers are removed
after use. ESLint remains unconfigured, so `expo lint` cannot run without setup.

All 17 stores were also browsed through native SQLite UI results, totaling 671
assignments, with no JavaScript fetch requests. All three demo stock labels were
confirmed in the rendered cards alongside unverified-product warnings.
